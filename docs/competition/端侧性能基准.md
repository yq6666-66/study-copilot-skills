# 端侧语义检索性能基准

> 本报告数字全部由 `scripts/bench.py` **真实运行**产出（2026-09-14，qwen3.8-flash 编程会话执行），
> 环境：Windows 11 / Python 3.14.0 / CPU（无 GPU）/ 模型 `BAAI/bge-small-zh-v1.5`（ONNX，512 维）。
> 语料为**程序合成的虚构错题文本**（科目×知识点模板 + 随机参数，不含任何真实题库），随机种子固定可复现。
> 复现：`python scripts/bench.py --size 2000 --queries 50`

## 结果

| 指标 | 300 条 | 2000 条 |
| --- | --- | --- |
| 首次建索引（含缓存落盘） | 0.92s | 7.23s |
| 增量更新（改 1%，走向量缓存） | **0.05s**（297 命中/3 重算） | **0.39s**（1980 命中/20 重算） |
| 无缓存全量重算同批 | 1.13s | 7.31s |
| **增量 vs 全量重算加速** | **约 22×** | **约 19×** |
| 单查询延迟 avg（embed + 向量检索） | 5.4 ms | 15.4 ms |
| 单查询延迟 p95 | 5.8 ms | 28.8 ms |

**结论**：千条级错题库上，端侧检索维持 **亚 30ms 查询、秒级全量、0.4s 增量**——普通笔记本 CPU 即可支撑每日复测节奏，学习数据全程不出本机。

## 基准驱动的两轮修正（诚实的开发记录）

本报告的数据来之不易——基准本身抓出了两个真问题并驱动修复：

1. **JSON 缓存负优化**：最初版本 `emb_cache.json` 用 JSON 序列化向量，300 条实测增量路径 **0.9×（比全量重算还慢）**，瓶颈在 1.8MB JSON 的读写解析。修复：改 `npz` 二进制（float32 + 压缩），并自动迁移旧 json。
2. **基准测量方法错误**：初版 bench 首建索引未走缓存路径，导致增量阶段"无缓存可命中"，测出的 1.0× 是假象。修复：首建改为走 `embed_cached`（模拟真实使用形态），才得到上表的 19-22× 真实加速。

两处均由 `tests/test_vec_cache.py` 固化回归（含 npz roundtrip、legacy 迁移、长 key 不截断等 8 个用例）。

> 复算口径：增量场景为「1% 条目文本修订」；查询延迟含单条 embed + 全库余弦检索，50 次取分位。
